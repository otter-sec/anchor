A Cross Program Invocation (CPI) is one program calling an instruction on another program. Composability on Solana is built on CPI. Token transfers, account creation through the System Program, and calls into another Anchor program all use it.

A CPI is constructed from the same three pieces as any Solana instruction:

1. The program ID of the program being called.
2. The accounts required by the instruction.
3. Any instruction data required as arguments.

Anchor's v2 CPI path keeps those pieces typed. `CpiContext<T>{:rs}` bundles the target program address, typed CPI accounts, signer seeds, and remaining accounts. `CpiHandle<'a>{:rs}` carries account handles into the CPI without exposing the raw account view for accidental re-borrows.

## System program CPI

`anchor_lang::system_program` provides typed wrappers for every System Program instruction. The wrappers take a `CpiContext{:rs}` whose accounts struct holds `CpiHandle<'a>{:rs}` values, so the call stays inside Anchor's borrow-tracked model.

```rust showLineNumbers=false
use anchor_lang::system_program;

#[derive(Accounts)]
pub struct Deposit {
    #[account(mut)]
    pub payer: Signer,
    #[account(mut)]
    pub vault: SystemAccount,
    pub system_program: Program<System>,
}

pub fn deposit(ctx: &mut Context<Deposit>, lamports: u64) -> Result<()> {
    let cpi = CpiContext::new(
        ctx.accounts.system_program.address(),
        system_program::Transfer {
            from: ctx.accounts.payer.cpi_handle_mut(),
            to: ctx.accounts.vault.cpi_handle_mut(),
        },
    );
    system_program::transfer(cpi, lamports)
}
```

The module exposes typed wrappers for the System Program instructions:

| Wrappers | Use for |
| --- | --- |
| `transfer{:rs}`, `create_account{:rs}`, `allocate{:rs}`, `assign{:rs}` | Ordinary signed account creation and lamport movement. |
| `*_with_seed{:rs}` variants of each | Cases where the base address is owned by another program and the resulting account address is derived deterministically. |
| The nonce-account family | Nonce account creation, withdrawal, authorization, and advance. |

## SPL token CPI

`anchor-spl` exposes account structs and helper functions for common SPL Token instructions. The example below transfers tokens with `transfer_checked{:rs}`.

The instruction needs a source token account, mint, destination token account, authority, and token program:

```rust showLineNumbers=false
#[derive(Accounts)]
pub struct TransferTokens {
    pub mint: Account<Mint>,
    #[account(
        mut,
        token::mint = mint,
        token::authority = authority,
    )]
    pub from: Account<TokenAccount>,
    #[account(mut, token::mint = mint)]
    pub to: Account<TokenAccount>,
    pub authority: Signer,
    pub token_program: Program<Token>,
}
```

The handler builds the CPI accounts, wraps them in `CpiContext{:rs}`, then calls the SPL helper:

```rust showLineNumbers=false
use anchor_spl::token;

pub fn transfer_tokens(
    ctx: &mut Context<TransferTokens>,
    amount: u64,
    decimals: u8,
) -> Result<()> {
    let accounts = token::accounts::TransferChecked {
        from: ctx.accounts.from.cpi_handle_mut(),
        mint: ctx.accounts.mint.cpi_handle(),
        to: ctx.accounts.to.cpi_handle_mut(),
        authority: ctx.accounts.authority.cpi_handle(),
    };

    let cpi = CpiContext::new(ctx.accounts.token_program.address(), accounts);
    token::transfer_checked(cpi, amount, decimals)
}
```

The account constraints protect the CPI from mismatched accounts before the Token Program runs. `token::mint = mint{:rs}` ensures both token accounts belong to the expected mint, and `token::authority = authority{:rs}` ensures the signer controls the source account.

## Generated Anchor CPI

When one Anchor program calls another Anchor program, the callee can expose generated CPI wrappers behind the `cpi{:toml}` feature. A caller can then use the callee's `program::cpi::accounts::*{:rs}` structs and wrapper functions.

```rust showLineNumbers=false
let cpi_accounts = callee::cpi::accounts::SetData {
    data: ctx.accounts.callee_data.cpi_handle_mut(),
    authority: ctx.accounts.authority.cpi_handle(),
};

let cpi_ctx = CpiContext::new(ctx.accounts.callee_program.address(), cpi_accounts);
callee::cpi::set_data(cpi_ctx, value)?;
```

The generated CPI account structs contain one `CpiHandle<'a>{:rs}` per account and implement `ToCpiAccounts<'a>{:rs}`. Wrapper functions pack instruction args and call `CpiContext::invoke{:rs}`.

## PDA signer seeds

A program can sign a CPI for a PDA derived from its own program ID. Program-owned vaults, authorities, and other accounts with no private key rely on this.

Attach signer seeds with `with_signer(){:rs}` when a PDA authorizes the CPI:

```rust showLineNumbers=false
let signer_seeds: &[&[&[u8]]] = &[&[
    b"vault-authority",
    ctx.accounts.mint.address().as_ref(),
    &[ctx.bumps.vault_authority],
]];

let cpi = CpiContext::new(ctx.accounts.token_program.address(), accounts)
    .with_signer(signer_seeds);
```

The outer slice can hold multiple signer PDAs. Each inner slice is the ordered seed list for one PDA, including its bump.

## After a CPI

Passing an account to a CPI with `cpi_handle_mut(){:rs}` hands the runtime
buffer to the callee. 
There are some differences from Anchor V1 to be aware of: under the new CPI design, stale account copy accesses are prevented by default,
avoiding the quite common bug class deriving from not calling `reload()` after a CPI.
In Anchor V2 instead, what you must do after the CPI returns depends on the account wrapper type.

### `BorshAccount<T>{:rs}`

`cpi_handle_mut(){:rs}` serializes pending edits and releases the borrow
before the call. This happens on every mutable handle, whether or not the
callee touches the account. After the CPI returns:

- any field read or write panics with `account borrow released`
- if the account is never reacquired, `exit(){:rs}` skips write-back

Reacquire before touching the account again:

```rust showLineNumbers=false
let cpi = CpiContext::new(
    ctx.accounts.other_program.address(),
    other::cpi::accounts::Update {
        profile: ctx.accounts.profile.cpi_handle_mut(),
    },
);
other::cpi::update(cpi)?;
ctx.accounts.profile.reacquire_borrow_mut()?;
ctx.accounts.profile.counter += 1;
```

`reacquire_borrow_mut(){:rs}` reruns the owner, discriminator, and size
checks and deserializes the post-CPI bytes, so the handler always sees what
the callee wrote. This replaces the v1 `reload(){:rs}` pattern.

Read-only handles from `cpi_handle(){:rs}` do not release the borrow.

### `Account<T>{:rs}` and `Slab<H, T>{:rs}`

Zero-copy wrappers read the account buffer directly, so data written by
the callee is visible immediately. There is nothing to reload.

The owner, discriminator, and length checks ran once at load and are not
repeated. They only go stale if the callee can change the account's owner/data/size:

- the CPI closes the account or assigns it to another owner
- the CPI reinitializes it as a different account type
- the CPI resizes it, changing a slab's capacity

A callee that cannot write to your program-owned account cannot do any of
these, so token transfers and similar CPIs need no extra step. If the CPI
goes back into your own program, or can close or resize the account because it owns it, call
`revalidate_after_cpi(){:rs}` before reading it again:

```rust showLineNumbers=false
self_program::cpi::reset(cpi)?;
ctx.accounts.ledger.revalidate_after_cpi()?;
```

Without it, reads after a shape change interpret the wrong bytes as `T{:rs}`
or index past the live data length.

### In essence

Briefly, here's what needs to be called after a CPI, whenever borrowed accounts are accessed after the fact:


| Wrapper | After `cpi_handle_mut(){:rs}` | Recovery |
| --- | --- | --- |
| `BorshAccount<T>{:rs}` | The borrow stays released and typed accesses panic until the lock is reacquired. | `reacquire_borrow_mut(){:rs}` |
| `Account<T>{:rs}`, `Slab<H, T>{:rs}` | Reads stay live but load-time checks are not rerun. | `revalidate_after_cpi(){:rs}` |



## `CpiHandle<'a>{:rs}`

`CpiHandle<'a>{:rs}` is intentionally narrow:

- `account.cpi_handle(){:rs}` creates a read-only handle
- `account.cpi_handle_mut(){:rs}` creates a writable handle and requires the account to be marked `mut{:rs}`
- `handle.address(){:rs}` returns the account address
- the handle does not deref to `AccountView{:rs}`

That missing `Deref{:rs}` is intentional. It prevents accidental use with checked pinocchio CPI builders that would re-borrow the same account views.

`CpiContext::invoke(data){:rs}` uses pinocchio's `invoke_signed_unchecked{:rs}`. The path stays safe for ordinary typed CPI because CPI account structs hold `CpiHandle<'a>{:rs}` values that borrow the typed account wrappers for the duration of the call.

Two layers catch aliasing:

- Rust rejects concurrent typed mutable access at compile time.
- pinocchio's account borrow state catches stale raw-borrow cases after the CPI returns.
